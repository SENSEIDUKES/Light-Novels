🌱 Brute: fix race condition in chapter sealing

Failure Tested:
Double-clicking the "Seal Chapter" button triggers multiple concurrent invocations of the `handleSealChapter` action.

Actual Behavior:
Because the previous implementation captured `isSealed` via an upstream read, rapid sequential clicks would all evaluate `isSealed` as `false`, causing `awardQi('chapter_sealed')` to be executed multiple times and multiple `scanChapterForArtifacts` tasks to be enqueued for the same chapter.

Expected Behavior:
Only the first seal operation should trigger side effects (Qi awards and artifact scanning).

Impact:
Users could double-click "Seal Chapter" to erroneously earn duplicate points and spam the artifact scanning background process.

Resolution:
Refactored `handleSealChapter` in `src/hooks/useChapterSealing.ts` to evaluate the chapter's `isSealed` state from within the store's `updateChapter` functional callback. The side-effects are now gated behind a `wasAlreadySealed` flag returned from the patch operation.

Verification:
Added `handleSealChapter seals the chapter and prevents multiple awards` to `src/hooks/useChapterSealing.test.ts` to simulate `Promise.all` overlapping invocations, confirming only one award is issued.

Limits:
No architectural changes were made to how `updateChapter` is implemented or enqueued, only how `handleSealChapter` utilizes it.
